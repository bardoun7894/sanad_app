# Admin Chat Display Name

## Overview

The admin chat system shows user names in the AppBar and in message headers. Display names are stored in the `support_chats/{userId}` thread doc as `user_name`. The system uses `resolveDisplayName` (from `lib/core/utils/user_display_name.dart`) to present the name — which explicitly filters out the string `'User'` (case-insensitive) as a placeholder guard.

## Name Resolution Strategy

Three layers ensure names are correct:

1. **Navigation layer** — When navigating from the mood feed, a `ChatThread` with the real name (already resolved by the provider) is passed via GoRouter `state.extra`. This gives the screen an immediate correct name without a Firestore read.

2. **Send-time resolution** — When the admin sends a message, if the current `thread.userName` is empty or `'User'`, the screen fetches the real name from `users/{userId}` using `resolveDisplayNameFromUserDoc`. This handles the case where old thread docs still have `'User'` stored.

3. **Service-layer guard** — The admin and user chat services never write `'User'` to Firestore. `sendAdminMessage` and `sendUserMessage` both check that the name is non-empty and not `'User'` before writing.

4. **Display-layer fallback** — `ChatThread.fallbackDisplayName` treats `'User'` as absent and falls back to the email, then to `'Unknown User'`. Added because the thread list card tested only `userName.isNotEmpty`, which a stored `'User'` passes.

5. **Async resolution in the list** — `AdminChatService.resolveDisplayNameForThread(thread)` combines the cached thread value with a `users/{userId}` read, performed only when the cached value is a placeholder. The list card and detail header wrap the label in a `FutureBuilder` so the email fallback renders immediately while the real name loads.

## Closing the write paths

The guard only holds if every path that writes `user_name` respects it. `broadcastMessageWithReport` did not — it wrote raw `userData['name']`, reintroducing `'User'` for accounts whose stored name is the placeholder. It now writes `resolveDisplayNameFromUserDoc(userData) ?? ''`. Replying from the detail screen additionally repairs a placeholder thread by writing the resolved real name.

Two placeholders exist, not one: `'User'` comes from legacy signup code and lives in the `users` collection, while `'Unknown User'` is generated by the display layer when no email is available. Fixing only one leaves the bug visible.

## Key Principle

Never write a placeholder string to Firestore that the display layer has to filter out. If the real name is not available at creation time, write nothing (empty string) and resolve it lazily at the point of use.
